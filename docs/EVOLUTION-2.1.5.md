## 3. Bug 修复

### 局部索引损坏无备份覆盖

旧逻辑仅在整个 JSONArray 无法解析时保全原文。若外层数组合法，但含字符串化记录、非对象、空 URI 对象等，读取会跳过这些条目；下一次收藏、移除或新增却只保存可读记录，导致不可读条目的恢复线索消失。损失的是索引原文，不是照片文件。

现在在共享偏好锁内读取并解析同一快照，比较原始数组长度与可读条目数；整体解析失败或发生跳过时，把完整原始字符串和替换索引放在同一次 `prefs.edit()`。每次损坏用独立 UUID 键，不覆盖历史快照；只读和无变化操作不写，不尝试猜测修复未知记录。

新增四项测试先在旧实现上实际运行，**4/4 失败**，均因恢复快照为空；修复后的照片仓库与缓存专项 **25/25 通过**，其中照片仓库 14 项、文件组件 11 项。覆盖精确原文、无变化不写、移除/撤销、重复损坏和跨 Repository 并发。

### 更新文件跨实例干扰

旧客户端共用 `lumora-update.part.apk` 与 `verified-update/lumora.apk`；另一个客户端开始下载或清理可删除已经 Ready 的文件。这是更新可靠性问题，不是任意 APK 安装漏洞。

新增 `UpdateCacheFiles`：每次尝试创建唯一部分文件，验签后才移到唯一的已验证路径；实例只登记、清理自己拥有的尝试。提升/清理受锁保护，clear 使旧 generation 失效；迟到、失败和取消只回滚对应尝试，包括从 IO 返回调用者之前的取消窗口。旧的已验证路径在本实例显式清理前保持不可变，其他客户端不删除它。进程退出遗留文件不全局清扫，交由系统缓存回收。

文件测试使用生产事务和真实 FileProvider；fixture 是文本而非签名 APK，只证明文件所有权、可读性和回滚，不能称为真实联网下载或 Android 安装器交互验收。

## 4. 性能与架构优化

- 索引重写复用同一个原始快照，不为损坏判断再次解析；没有做吞吐或延迟基准，因此不报告百分比提速。
- 缓存所有权从网络/包身份校验分离，生产 `download()` 仍在交付前运行原 `verifyArchive()`，安装前再次验证；未扩展 FileProvider 路径。
- 同一客户端正常 UI 只接受当前 Available/Ready 对应的 offer，不增加任意多版本安装接口。
- 无新依赖、无目录级删除、无照片 IO 变更、无数据迁移。旧会话残留缓存的限额回收需要安装会话租约设计，不能凭文件年龄删包。
